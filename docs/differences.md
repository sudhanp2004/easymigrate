# AWS → GCP differences

Generated by `scripts/gen_differences_doc.py` from the rule catalogue. Do not edit by hand.

## AWS subnets are single-zone; GCP subnets span the region (`NET-ZONE-REGIONAL`)

AWS subnets each live in one availability zone. A GCP subnet spans an entire region, so zone isolation at the subnet level cannot be reproduced exactly.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `keep_1to1` | One GCP subnet per AWS subnet | same CIDRs; zone isolation is lost at the subnet level | low |  | yes |
| `merge_per_network` | Merge into one regional subnet per network | one regional subnet covering the smallest CIDR that contains them; IPs may change | high |  |  |

## GCP routes are network-wide; isolation must be enforced per VM (`NET-ISOLATION-VM-LEVEL`)

An isolated AWS subnet has no route to the internet. On GCP, routes are network-wide, so isolation for this subnet's resources must come from having no external IP rather than from subnet routing.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `no_external_ip` | Enforce isolation with no external IP | resources in this subnet get no external IP; later plugins enforce this | medium |  | yes |
| `manual` | Handle manually | no change made | low | yes |  |

## GCP egress rules cannot target another firewall policy's tag (`NET-EGRESS-TAG`)

An AWS egress rule can target another security group directly. GCP egress rules can only target CIDR ranges, so the peer policy's tag must be translated to ranges.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `peer_attached_ranges` | Target the peer's attached ranges | destination becomes the peer's network CIDR blocks (applies_to is not yet known) | medium |  | yes |
| `manual` | Handle manually | the egress rules are omitted | low | yes |  |

## GCP has no equivalent of a cross-VPC security group reference (`NET-SG-XVPC-REF`)

An AWS rule can reference a security group in another VPC or account. GCP firewall rules cannot reference a policy outside this migration.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `manual` | Handle manually | the rule is omitted; recreate it after migrating the peer network | low | yes | yes |

## IPv6 is migrated separately, if at all (`NET-IPV6`)

GCP dual-stack support has different rules than AWS. A subnet that was public only through IPv6 is recorded as `isolated` once migrated IPv4-only, since it no longer has any public path.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `ipv4_only` | Migrate IPv4 only | ipv6_cidr_blocks/ipv6_cidr are cleared on the network and its subnets | medium |  | yes |
| `manual` | Handle manually | the same change as ipv4_only, but requires acknowledgement | medium | yes |  |

## Overlapping CIDRs are allowed on GCP, for now (`NET-CIDR-OVERLAP`)

AWS VPCs with overlapping CIDRs coexist because they are isolated. GCP networks are isolated too, but connecting these networks later (peering, a shared VPC) will conflict.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `keep` | Keep both networks as they are | no change | none |  | yes |

## AWS engine versions do not line up with Cloud SQL's supported majors (`DB-ENGINE-VERSION`)

Cloud SQL supports a specific set of major versions per engine. A source major outside that set cannot be created as-is; the engine must be upgraded.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `nearest_major` | Use the nearest Cloud SQL major version | database_version set for the source major; the patch level is Google's to choose | low |  | yes |
| `upgrade_to_oldest_supported` | Upgrade to Cloud SQL's oldest supported major | database_version set to the oldest supported major; an engine upgrade with application-visible behaviour changes | high |  |  |
| `manual` | Handle manually | excluded | low | yes |  |

## AWS instance classes do not map onto Cloud SQL machine tiers (`DB-TIER`)

Cloud SQL bills by custom or shared-core tier, not by AWS instance class name; the nearest equivalent must be computed from vCPU and memory.

| `shared_core` | Use a shared-core tier | db-f1-micro or db-g1-small, chosen from the source burstable class | medium |  |  |
| `manual` | Handle manually | excluded | low | yes |  |

## A private RDS instance needs Private Services Access on Cloud SQL (`DB-PRIVATE-IP`)

Cloud SQL's private IP is reached through Private Services Access, which needs an allocated IP range peered to the VPC; there is no direct VPC attachment.

## A publicly accessible RDS instance has no direct Cloud SQL equivalent (`DB-PUBLIC-ACCESS`)

Cloud SQL's public IP has no VPC-native concept of a security group; access is restricted by an authorized-networks CIDR allow list instead.
