# AWS → GCP differences

Generated by `scripts/gen_differences_doc.py` from the rule catalogue. Do not edit by hand.

## Network rules

### AWS subnets are single-zone; GCP subnets span the region (`NET-ZONE-REGIONAL`)

AWS subnets each live in one availability zone. A GCP subnet spans an entire region, so zone isolation at the subnet level cannot be reproduced exactly.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `keep_1to1` | One GCP subnet per AWS subnet | same CIDRs; zone isolation is lost at the subnet level | low |  | yes |
| `merge_per_network` | Merge into one regional subnet per network | one regional subnet covering the smallest CIDR that contains them; IPs may change | high |  |  |

### GCP routes are network-wide; isolation must be enforced per VM (`NET-ISOLATION-VM-LEVEL`)

An isolated AWS subnet has no route to the internet. On GCP, routes are network-wide, so isolation for this subnet's resources must come from having no external IP rather than from subnet routing.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `no_external_ip` | Enforce isolation with no external IP | resources in this subnet get no external IP; later plugins enforce this | medium |  | yes |
| `manual` | Handle manually | no change made | low | yes |  |

### GCP egress rules cannot target another firewall policy's tag (`NET-EGRESS-TAG`)

An AWS egress rule can target another security group directly. GCP egress rules can only target CIDR ranges, so the peer policy's tag must be translated to ranges.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `peer_attached_ranges` | Target the peer's attached ranges | destination becomes the CIDRs of the subnets hosting the peer's instances, or the peer's network CIDR blocks when no migrated instance is behind it | medium |  | yes |
| `manual` | Handle manually | the egress rules are omitted | low | yes |  |

### GCP has no equivalent of a cross-VPC security group reference (`NET-SG-XVPC-REF`)

An AWS rule can reference a security group in another VPC or account. GCP firewall rules cannot reference a policy outside this migration.

## Compute rules

### An AMI cannot be moved to GCP, and a disk's contents do not migrate (`VM-BOOT-IMAGE`)

EasyMigrate does not import, convert or rebuild AMIs, and does not copy disk contents. A migrated instance boots a current stock image of the nearest distribution: the machine runs, on the right network, at the right size, with nothing that was installed or stored on the source disk.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `stock_image` | Boot a stock GCP image | the instance boots a current stock image chosen from the source platform; everything that was on the source disk is absent | high |  | yes |
| `manual` | Handle manually | nothing is generated for this instance | low | yes |  |

Params:

- `image_family`: GCP image family, e.g. debian-12
- `image_project`: GCP image project, e.g. debian-cloud

### A GCP stock image needs a bigger boot disk than the source root volume (`VM-BOOT-DISK-MINIMUM`)

Every Compute Engine image carries a minimum boot-disk size and the API refuses anything smaller. An AWS AMI of the same distribution routinely fits in less, so a root volume that was legal in AWS can be too small for the image replacing it.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `grow_to_minimum` | Grow the boot disk to the image's minimum | the boot disk is created at the image's minimum size instead of the source's | none |  | yes |

### EC2 instance types and GCP machine types do not line up (`VM-MACHINE-TYPE`)

GCP predefined machine types come in fixed memory-per-vCPU ratios, and AWS families do not share them. EasyMigrate never reduces memory, so a source whose ratio GCP has no type for gains memory, which costs more.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `nearest_predefined` | Nearest predefined machine type | same vCPU count, the smallest predefined type whose memory is at least the source's; the report names the exact delta | low |  | yes |
| `custom_machine_type` | Custom machine type | exact vCPU and memory via a custom type, at a higher per-unit price and without committed-use discounts | medium |  |  |
| `manual` | Handle manually | nothing is generated for this instance | low | yes |  |

### AWS availability-zone names carry no meaning a GCP zone preserves (`VM-ZONE-MAPPING`)

An AWS AZ letter is a per-account alias over a stable AZ id, so `ap-south-1a` is a different physical zone for different accounts. Zones are therefore assigned by position: instances that shared an AZ stay together, and instances that were spread stay spread, but no letter is preserved.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `positional` | Assign zones by position | distinct source zones are sorted and mapped to the destination region's zones in order; co-location and spread are preserved, letters are not | low |  | yes |
| `manual` | Handle manually | nothing is generated for this instance | low | yes |  |

### A reachable-from-the-internet instance stays reachable unless you say otherwise (`VM-PUBLIC-IP`)

An instance with a public address is reachable from the internet, governed only by its firewall rules. Recreating that exposure without asking would change the security posture of a machine the user may not have reviewed, so the default is to give the instance no external address.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `private_only` | No external IP | the instance has no external address; every client must reach it from inside the VPC or through a bastion. This matches nothing in the source | medium |  | yes |
| `ephemeral_external` | Keep an ephemeral external IP | the instance stays reachable from the internet on a new, non-reserved address, governed only by the migrated firewall rules | high |  |  |
| `static_external` | Reserve a static external IP | as above, with a reserved address, so the instance keeps a stable public endpoint; it is billed whether or not it is in use | high |  |  |

### A stopped instance should not start billing on arrival (`VM-STOPPED`)

An instance the customer deliberately stopped costs nothing in AWS. Creating it running in GCP would start charging for it without anyone asking.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `create_stopped` | Create it stopped | the instance is created and immediately left in TERMINATED state | none |  | yes |
| `create_running` | Create it running | the instance is created running, and billing starts at apply time | medium |  |  |

### Persistent disk performance scales with size; EBS provisions it directly (`VM-DISK-TYPE`)

An EBS volume can be given IOPS and throughput independently of its size. A persistent disk cannot: its performance follows its size and type, so provisioned figures do not carry and a small disk may be slower than the source.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `nearest_pd` | Nearest persistent disk type | io1/io2 become pd-ssd, st1/sc1 become pd-standard, gp2/gp3 become pd-balanced; provisioned IOPS and throughput are lost | medium |  | yes |
| `hyperdisk` | Hyperdisk | provisioned IOPS and throughput are preserved, at a different price and with machine-type and zone availability limits | medium |  |  |
| `manual` | Handle manually | nothing is generated for this disk | low | yes |  |

### A data volume is recreated empty (`VM-DISK-EMPTY`)

EasyMigrate does not copy disk contents. A non-boot volume is recreated at the same size and type with nothing on it. A mounted empty disk is a subtler failure than a missing one, which is why this carries the same risk as the boot image.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `create_empty` | Create an empty disk | a persistent disk of matching size and type is created and attached, containing nothing from the source volume | high |  | yes |
| `omit` | Do not create it | the disk is reported and not created; the instance comes up without it | medium |  |  |

### A customer-managed KMS key does not carry to GCP (`VM-DISK-ENCRYPTION`)

An EBS volume encrypted with a customer-managed AWS KMS key cannot use that key in GCP. The disk stays encrypted at rest either way; what changes is who holds the key.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `google_managed` | Google-managed encryption | the disk is encrypted at rest with Google-managed keys | low |  | yes |
| `manual` | Handle manually | create a Cloud KMS key, grant the Compute Engine service agent, and set disk_encryption_key yourself | low | yes |  |

### Instance-store volumes become fixed-size local SSDs (`VM-INSTANCE-STORE`)

Both clouds lose the data when the machine stops. GCP local SSD comes in fixed 375 GiB devices and requires a machine type that supports it, so the size rarely matches the source exactly.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `local_ssd` | Attach local SSD | whole 375 GiB local SSD devices are attached, rounded up; the machine type must support local SSD | medium |  | yes |
| `omit` | Do not attach it | the ephemeral volume is reported and not recreated | low |  |  |

### An EC2 key pair becomes a GCP SSH key, or GCP's own access model (`VM-SSH-KEYS`)

AWS injects one key pair into an instance at launch. GCP reads SSH keys from instance metadata, or delegates access to IAM through OS Login. EasyMigrate never generates a key pair; it carries the public key AWS still holds, or lets you choose another model.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `import_public_key` | Import the key pair's public key | the public key AWS holds becomes an ssh-keys metadata entry for the same login | low |  | yes |
| `os_login` | Use OS Login | the key pair is ignored and GCP IAM governs who may log in; this changes the access model, so every current user needs an IAM grant | medium |  |  |
| `user_supplied_key` | Use a public key you supply | the public key you give becomes an ssh-keys metadata entry | low |  |  |
| `no_ssh_access` | No SSH access | no key is added and project-wide SSH keys are blocked; nobody can log in over SSH until access is configured | medium |  |  |

Params:

- `public_key`: an OpenSSH public key, e.g. 'ssh-ed25519 AAAA… you@host'
- `username`: login name the key is installed for, e.g. ec2-user

### EC2 user data becomes a GCP startup script, which runs on every boot (`VM-USER-DATA`)

AWS runs user data once, on first boot, through cloud-init. GCP's guest agent runs a startup script on every boot and does not interpret #cloud-config. A script that is not safe to run twice needs a guard before it migrates.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `startup_script` | Run it as a startup script | copied verbatim into the startup-script metadata key; it runs on every boot, not first boot only, and #cloud-config is not interpreted | medium |  | yes |
| `cloud_init` | Pass it to cloud-init | written to the user-data metadata key, which only images that ship cloud-init honour; GCP's Debian, Rocky and RHEL images do not | medium |  |  |
| `omit` | Do not carry it | the script is reported in full and not run on the new instance | low |  |  |

### An instance profile's IAM role is not translated (`VM-IAM-PROFILE`)

An EC2 instance profile gives software on the machine AWS credentials. GCP service accounts have different semantics, and translating permissions is out of scope, so whatever the software did with those credentials stops working.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `manual` | Handle manually | the instance is created with no service account; the AWS role is named in the report so you can create and attach a service account with equivalent access | medium | yes | yes |

### AWS Spot and GCP Spot VMs are preempted differently (`VM-SPOT`)

Both clouds reclaim spot capacity at short notice, but AWS gives a two-minute interruption notice through instance metadata while GCP gives thirty seconds through an ACPI shutdown. Handlers written for one do not fire on the other.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `spot_vm` | Create a Spot VM | provisioning model SPOT, stopped rather than deleted on preemption, and never restarted automatically | medium |  | yes |
| `standard` | Create a standard VM | the instance costs more and is never preempted | low |  |  |

### Dedicated tenancy is not reproduced (`VM-TENANCY`)

GCP's equivalent is sole-tenant nodes, which need a node template, a node group and affinity labels. This family does not generate them.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `manual` | Handle manually | the instance is created on shared hardware; create a sole-tenant node group and set node affinity yourself if isolation or licensing requires it | medium | yes | yes |

### A placement group is not reproduced (`VM-PLACEMENT-GROUP`)

Cluster, spread and partition placement groups correspond to GCP resource policies with different guarantees. This family does not generate them.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `manual` | Handle manually | the instance is created without placement constraints; attach a GCP placement policy yourself if latency or failure isolation depended on the group | medium | yes | yes |

### GCP's metadata server has no IMDSv2 token protocol (`VM-IMDS`)

The source requires IMDSv2 session tokens. GCP's metadata server instead requires a `Metadata-Flavor: Google` header on every request and has no v1/v2 distinction. Software that calls the AWS metadata endpoint needs changing regardless.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `note_only` | Note it | nothing to configure: GCP's header requirement already blocks the SSRF-style requests IMDSv2 was introduced to stop | none |  | yes |

### Termination protection becomes deletion protection (`VM-TERMINATION-PROTECTION`)

GCP's deletion protection refuses a delete exactly as AWS termination protection does.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `deletion_protection` | Enable deletion protection | the instance cannot be deleted until deletion protection is turned off | none |  | yes |

### An unattached Elastic IP becomes a reserved address, with a different IP (`VM-ELASTIC-IP-UNATTACHED`)

An Elastic IP nobody uses is usually kept for a reason — an allow-list entry or a DNS record. GCP can reserve an address, but not the same one, so whatever depended on the old IP needs updating either way.

| Strategy | Title | Effect | Risk | Manual | Default |

### An Auto Scaling group becomes a managed instance group (`VM-ASG-SHAPE`)

An ASG spanning availability zones maps to a regional managed instance group, which spreads instances across the mapped GCP zones. A GCP subnet is regional, so one subnet serves every zone where AWS used one per AZ. Instances are created with no external IP.

## Kubernetes rules

### The GKE cluster is created empty (`K8S-EMPTY-CLUSTER`)

EasyMigrate migrates the cluster, not what runs in it. No Deployments, Services, ConfigMaps, Secrets, custom resources, Helm releases or persistent volumes are read or copied: the Kubernetes API is never called.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `note_only` | Understood | the cluster and its node pools are created with nothing deployed; every workload must be redeployed from its source of truth | high |  | yes |

### The Kubernetes version and upgrade policy change hands (`K8S-VERSION`)

EKS keeps a cluster on its minor until the user upgrades it or support ends. Every new GKE cluster is in a release channel and upgrades automatically; the Extended channel is the closest to EKS, holding a minor for longest.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `pin_minor` | Pin the same minor on the Extended channel | the cluster starts on the source minor (or the nearest newer one GKE offers) in the Extended channel, which keeps a minor longest; patch versions still upgrade automatically, and the extended-support period is billed extra | low |  | yes |
| `regular_channel` | Enrol in the Regular release channel | GKE picks the version and upgrades control plane and nodes automatically | medium |  |  |

### The API endpoint's exposure is reproduced, not narrowed (`K8S-ENDPOINT`)

EKS exposes the Kubernetes API publicly, privately or both, with an optional CIDR allow-list. GKE has a public endpoint guarded by authorized networks, or a private one. EasyMigrate mirrors the source so kubectl keeps working from where it worked before.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `mirror` | Mirror the source exposure | a public endpoint with the same allow-list as authorized networks, or a private endpoint when EKS was private-only | low |  | yes |
| `private_endpoint` | Private endpoint only | the API is reachable only from inside the VPC; kubectl from outside stops working | medium |  |  |

### Nodes get no external IP unless you ask for one (`K8S-PRIVATE-NODES`)

EKS nodes in public subnets get public addresses. A GKE node with no external IP reaches the internet only through Cloud NAT, so image pulls from public registries need NAT on the node subnet; Google's own registries are reached privately.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `private_nodes` | Private nodes | nodes have no external IPs; pulling from Docker Hub or other public registries needs Cloud NAT on the node subnet | medium |  | yes |
| `public_nodes` | Public nodes | every node has an external IP, reachable from the internet as the firewall allows | high |  |  |

### Pods move from VPC addresses to a secondary range (`K8S-POD-RANGES`)

EKS's VPC CNI gives every pod an address from the node's subnet. GKE takes pod and service addresses from secondary ranges on one subnet, so pods no longer hold VPC addresses: anything that allow-listed pod IPs, or relied on security groups for pods, must change.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `secondary_ranges` | Add pod and service ranges to the node subnet | the chosen subnet gains a pods range and a services range; the EKS service CIDR is kept when it overlaps nothing, so in-cluster DNS keeps its address | medium |  | yes |

Params:

- `pods_cidr`: pod range, /21 or larger, overlapping nothing in the network
- `services_cidr`: service range, /27 or larger, overlapping nothing in the network
- `subnet`: IR id of the subnet the cluster and its node pools use

### Control-plane log types map to GKE logging components (`K8S-LOGGING`)

EKS ships selected control-plane logs to CloudWatch. GKE sends component logs to Cloud Logging; audit logs are Cloud Audit Logs, and the authenticator log has no equivalent.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `map_components` | Map each log type | api, controllerManager and scheduler become the matching GKE components, plus system components; container logs are not enabled, as on EKS | low |  | yes |

### A KMS key for Kubernetes secrets does not carry to GCP (`K8S-SECRETS-ENCRYPTION`)

EKS envelope-encrypts secrets with the customer's KMS key. GKE encrypts etcd at rest with Google-managed keys; application-layer encryption needs a Cloud KMS key.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `google_managed` | Google-managed encryption | secrets are encrypted at rest by Google, without application-layer encryption | low |  | yes |
| `manual` | Handle manually | create a Cloud KMS key and set database_encryption on the cluster yourself | low | yes |  |

### EKS add-ons map to GKE built-ins, or are not migrated (`K8S-ADDONS`)

The VPC CNI, kube-proxy and CoreDNS are part of every GKE cluster, and the Persistent Disk CSI driver replaces the EBS one. The EFS driver maps to Filestore. Any other add-on must be reinstalled; storage classes naming AWS provisioners must change either way.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `map_addons` | Map each add-on | built-ins are used, Filestore CSI is enabled for EFS, and the rest are listed | low |  | yes |

### IAM roles for service accounts are not translated (`K8S-IAM-FOR-PODS`)

Pods that assumed AWS roles through IRSA or EKS Pod Identity lose those credentials. Workload Identity is enabled on the GKE cluster so each binding can be recreated as a Google service account, but EasyMigrate does not translate permissions.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `manual` | Recreate the bindings yourself | Workload Identity is on; every listed service account needs a Google service account with equivalent access and an IAM binding | high | yes | yes |

### Who can use the cluster must be granted again (`K8S-CLUSTER-ACCESS`)

| Strategy | Title | Effect | Risk | Manual | Default |

### An IPv6 cluster is generated IPv4-only (`K8S-IPV6`)

| Strategy | Title | Effect | Risk | Manual | Default |

| Strategy | Title | Effect | Risk | Manual | Default |

### ACL-enabled buckets become uniform-access buckets (`S3-ACLS`)

| Strategy | Title | Effect | Risk | Manual | Default |

### A customer-managed KMS key does not carry to GCP (`S3-ENCRYPTION-KMS`)

Objects were encrypted with the customer's AWS KMS key. Cloud Storage encrypts at rest with Google-managed keys by default; a customer-managed key needs Cloud KMS.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `google_managed` | Google-managed encryption | objects are encrypted at rest with Google-managed keys | low |  | yes |
| `manual` | Handle manually | create a Cloud KMS key and set the bucket's default encryption yourself | low | yes |  |

### Lifecycle rules map to Cloud Storage lifecycle actions (`S3-LIFECYCLE`)

Transitions, expirations and multipart clean-up carry, with S3 storage classes mapped to the nearest Cloud Storage class. Rules filtered by object tags or size cannot be expressed and are dropped. Cloud Storage bills minimum storage durations of 30, 90 and 365 days for Nearline, Coldline and Archive.

| Strategy | Title | Effect | Risk | Manual | Default |
|---|---|---|---|---|---|
| `map_rules` | Map each rule | every expressible rule is generated; the rest are listed in the report | low |  | yes |

### Intelligent-Tiering becomes Autoclass (`S3-INTELLIGENT-TIERING`)

| Strategy | Title | Effect | Risk | Manual | Default |

| `autoclass` | Enable Autoclass | Cloud Storage moves each object to the class its access pattern warrants; lifecycle storage-class transitions are dropped, since Autoclass refuses them | low |  | yes |
| `standard` | Stay in Standard | objects stay in Standard unless a lifecycle rule moves them | low |  |  |

### Allowed and exposed CORS headers merge into one list (`S3-CORS`)

Cloud Storage keeps one header list per CORS rule: it allows those request headers in a preflight and exposes those response headers. S3 keeps two. Merging them carries both, and also exposes the allowed headers — slightly wider than the source.

| Strategy | Title | Effect | Risk | Manual | Default |

### Static website hosting has no s3-website endpoint on GCP (`S3-WEBSITE`)

| Strategy | Title | Effect | Risk | Manual | Default |

### Server access logs become Cloud Storage usage logs (`S3-ACCESS-LOGGING`)

| Strategy | Title | Effect | Risk | Manual | Default |

A Cloud Storage retention policy keeps every object for a minimum period. Unlocked, an admin can remove it — weaker than S3 Compliance mode. Locked, it can never be shortened or removed, and the bucket cannot be deleted until every object ages out.

| Strategy | Title | Effect | Risk | Manual | Default |

### Event notifications are not reproduced (`S3-NOTIFICATIONS`)
